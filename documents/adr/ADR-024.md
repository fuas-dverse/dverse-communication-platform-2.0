# ADR-024: Tauri as the Desktop Client Shell

**Status:** Accepted
**Project:** DVerse Communication Platform 2.0
**Author:** Denis Lorenzo Neagoe
**Date:** 08-06-2026

---

## Context

The DVerse chat application needs a native desktop client on macOS (and eventually Linux/Windows). The client must host a web-based chat UI, launch and manage background processes (the Python backend and the local Zenoh router), and integrate with the broader Rust workspace that already contains `zenoh_router`, `ping`, `pong`, and `bot_framework`.

The team evaluated Electron, a custom native application, and Tauri as shells for the web frontend.

The project's primary language is Rust. The Zenoh router and agent nodes are all written in Rust and live in the same Cargo workspace. Tauri's backend is also written in Rust, which means client-side OS integration, process management, and IPC can share the workspace's existing crates, tooling, and CI pipeline without introducing a second language runtime.

## Decision

Use Tauri 2 as the desktop shell for the DVerse chat client.

The Tauri application (`src/zenoh_client_launcher`) hosts the React/Vite frontend in a WebView and manages the lifecycle of the Python FastAPI backend process. The Tauri backend exposes Rust commands to the frontend via IPC for operations that require native access (process control, file system, system tray). The build configuration at `src/zenoh_client_launcher/src-tauri/tauri.conf.json` controls the bundled identifier, window settings, and allowed IPC commands.

## Alternative Decisions

**Electron.** Rejected. Electron bundles a full Chromium and Node.js runtime, producing binaries of 100–200 MB for a shell that would contain only a WebView wrapper and process-launch logic. Node.js adds a second runtime with no connection to the existing Rust workspace, and Electron's IPC model (contextBridge, preload scripts) is more boilerplate-heavy than Tauri's typed command interface. Security defaults are weaker: Electron gives the renderer full Node.js access unless the developer actively restricts it; Tauri's allowlist inverts this default.

**Custom native application (pure Rust, no WebView).** Rejected. Rewriting the chat UI in a native Rust UI framework (egui, Slint, Dioxus) would duplicate the existing React components and disconnect the UI from the web-based design system. It would also block frontend contributors who are not familiar with Rust.

**Ship a browser-only web app (no desktop shell).** Rejected for this sprint. The platform requires launching the Python backend and local Zenoh router as managed subprocesses tied to the client's lifetime. A browser tab cannot manage OS-level process lifecycles or connect to local Zenoh network interfaces without a native intermediary.

## Consequences

### Positive

- Tauri backend code is Rust and shares the Cargo workspace with `zenoh_router` and agent crates.
- Binary size is small: Tauri ships only the OS WebView, not a bundled Chromium.
- Allowlist-based IPC reduces attack surface compared to Electron's default full-Node renderer.
- The same Vite build output used during development is served by the Tauri WebView in production — no separate build path for the frontend.

### Negative

- WebView rendering differs across platforms (WebKit on macOS, WebView2 on Windows). CSS behaviour must be tested on each target OS.
- Tauri's IPC is typed at the Rust/TypeScript boundary via generated bindings; changes to Rust command signatures require regenerating types on the frontend side.
- Launching and monitoring the Python backend subprocess from Tauri requires careful handling of process cleanup on window close, which adds Tauri-specific logic to the launcher crate.
