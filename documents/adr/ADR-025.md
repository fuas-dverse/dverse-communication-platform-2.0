# ADR-025: Chat Application ↔ Zenoh Communication and Bot Registration

**Status:** Accepted
**Project:** DVerse Communication Platform 2.0
**Author:** Denis Lorenzo Neagoe
**Date:** 08-06-2026

---

## Context

The DVerse chat application must support AI bot participants that are decoupled from the Python backend. Bots may run on any machine, be written in any language, and connect to the same Zenoh router the rest of the platform uses. The backend must route user messages to the correct bot, collect the response, and deliver it to the room without blocking the FastAPI event loop.

Several constraints shaped the design:

- Zenoh's Python SDK is synchronous and callback-driven. Its callbacks fire on an internal Zenoh thread, not on the `asyncio` event loop that FastAPI runs on.
- Bots are autonomous processes. The backend cannot know in advance which bots are running, on which machines, or for how long.
- Bot identity must be lightweight: no pre-registration database, no admin step. A bot should be addable to a room by sharing a single secret token.

## Decision

### Topic layout

Four Zenoh key expressions carry all chat↔bot traffic:

| Key expression | Direction | Purpose |
|---|---|---|
| `chat/{room_id}/request/{bot_name}` | backend → bot | Deliver a user message to a named bot |
| `chat/response/{request_id}` | bot → backend | Return the bot's reply keyed by request correlation ID |
| `chat/presence/{bot_name}` | bot → backend | Periodic heartbeat advertising the bot's identity |

### Request/response flow

1. A user sends a message starting with `@{bot_name}` in a room.
2. The backend generates a `request_id` (UUID), stores an `asyncio.Future` for it, and publishes to `chat/{room_id}/request/{bot_name}` with payload `{ request_id, room_id, bot_name, message, history }`.
3. The bot agent subscribes to `chat/+/request/{bot_name}`, receives the message, calls its LLM, and publishes to `chat/response/{request_id}` with payload `{ request_id, content }`.
4. The `ZenohBridge._on_response` callback (running on Zenoh's internal thread) resolves the waiting `Future` via `loop.call_soon_threadsafe`, returning control to FastAPI's async handler.
5. If no response arrives within 60 seconds the `Future` times out and the backend returns an error to the client.

### Presence and bot discovery

Bots publish a heartbeat to `chat/presence/{bot_name}` every 30 seconds. The payload is:

```json
{
  "name": "mybot",
  "description": "Short description",
  "platform": "zenoh",
  "capabilities": ["chat"],
  "token_hash": "<sha256 of secret token>"
}
```

The backend's `_on_presence` callback maintains a `BotPresence` registry. A bot is considered online if its last heartbeat arrived within 90 seconds (`PRESENCE_TTL`). The `GET /bots/available` endpoint returns all online bots, omitting `token_hash`.

### Bot registration (token model)

Adding a bot to a room requires the user to supply the bot's token. The backend calls `ZenohBridge.verify_bot_token(bot_name, token)`, which compares `sha256(token)` against the hash the bot published in its presence payload. No database entry is created — the token is validated at the point of use. If the bot goes offline and comes back with a new token, the hash in the registry is updated on the next heartbeat.

### Asyncio/Zenoh thread handoff

`ZenohBridge` runs its Zenoh session in a `ThreadPoolExecutor` thread launched during FastAPI startup. Callbacks invoked by Zenoh (`_on_response`, `_on_presence`) use `loop.call_soon_threadsafe` to safely post results onto the asyncio event loop. Publish operations (`session.put`) are executed via `asyncio.get_event_loop().run_in_executor` so they do not block the async handler.

## Alternative Decisions

**HTTP webhooks from bots to the backend.** Rejected. Bots would need to know the backend's address and the backend would need an inbound port reachable from each bot machine. Zenoh pub/sub removes the need for any direct addressing — both backend and bot connect to the shared router.

**Zenoh queryable (request/reply primitive).** Considered. Zenoh's built-in queryable would eliminate the manual `request_id` correlation. Rejected because the Python SDK's queryable API is synchronous and the reply callback's threading model is less predictable than a simple pub/sub callback. The explicit `request_id` correlation is transparent and easy to trace with OpenTelemetry.

**Pre-registration: bots stored in the database.** Rejected. A database record would require an admin action each time a bot is deployed or updated. The heartbeat-plus-token model allows zero-config bot deployment: run `bot_agent.py`, share the printed token with a room user, done.

**Per-bot Zenoh key (no room scoping).** Rejected. Including `room_id` in the request key (`chat/{room_id}/request/{bot_name}`) allows bots to subscribe selectively or fan-out to multiple rooms. It also preserves routing context on the Zenoh layer without embedding it in the payload.

## Consequences

### Positive

- Bots are fully decoupled: any language, any machine, no backend modification needed to add a new bot.
- The token model requires no database schema change or admin UI — token validation is a single SHA-256 comparison.
- The presence TTL automatically removes offline bots from the available list without a separate cleanup job.
- OpenTelemetry spans on `zenoh.bot_request` capture room, bot name, request ID, and latency for every request/response pair.

### Negative

- The 90-second presence TTL means a freshly restarted bot may be invisible for up to one heartbeat interval (30 s) before the backend considers it online.
- The `asyncio`/Zenoh thread boundary requires careful use of `call_soon_threadsafe` and `run_in_executor`. Direct asyncio calls from Zenoh callbacks will silently corrupt the event loop.
- If the bot publishes a response after the 60-second timeout, the response is silently dropped (the `Future` is no longer in `_pending`). The bot is not notified of the timeout.
- Token security depends on Zenoh transport security. On an untrusted network the token hash travels in plaintext over Zenoh unless mTLS is enabled (see ADR-005, ADR-017).
