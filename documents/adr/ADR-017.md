# ADR-017: Present the router's client certificate on outgoing inter-router TLS connections

**Status:** Accepted
**Date:** 28-05-2026
**Author:** Yordan Mitev

## Context

After PR #89 / #90 / #91, two routers on the same LAN discover each other via DNS-SD, agree on session identity, and end up with each other's `tls/<ip>:<port>` endpoint in their respective Zenoh `connect/endpoints` lists. Their listener sockets each present a server certificate; mutual TLS is mandatory.

`build_zenoh_config` was setting only two TLS fields:

```
listen_certificate    = router.crt
listen_private_key    = router.key
```

These configure the **listener** side. They control which certificate the router presents when a peer dials *us*. They do **not** configure the **dialer** side. When the router dials a peer, it terminates the handshake without offering any client certificate at all. The peer (running `enable_mtls = true` exactly as we do) requires a valid client cert and aborts the handshake.

The failure mode is silent across multiple layers:

* mDNS discovery succeeds — both routers find each other.
* Endpoints land in `connect/endpoints` correctly.
* The router restarts its Zenoh session as designed.
* The new session reloads its ACL with the peer's CN admitted.
* The TLS handshake on the outbound connection stalls without an obvious error in either router's GUI; Zenoh just keeps retrying.
* No agent message ever crosses the LAN.

The symptom only shows up in two-machine testing — locally the router both dials and accepts on the same listener and the bug is invisible — which is why it survived until #91 stabilised.

## Decision

Set the corresponding **connect**-side fields to the same files the listener uses:

```
listen_certificate     = router.crt
listen_private_key     = router.key
connect_certificate    = router.crt
connect_private_key    = router.key
```

A router has exactly one identity. It uses the same cert in both directions; the listener / connect split inside Zenoh's TLS config is a configuration-surface oddity, not an indication that two identities should exist. No new files, no new config keys, no new code path.

## Alternatives

**Issue a separate client certificate for outgoing connections.** Rejected. Adds an issuance round-trip and a second cached file per router for no security or operational benefit. Step-CA has no reason to distinguish "this router as a TLS server" from "this router as a TLS client" — both roles map to the same `CN`.

**Disable mTLS on the listener so peer connects don't need a client cert.** Rejected. The entire trust model depends on mutual TLS — every connection is authenticated to a step-CA-issued identity. Downgrading to server-auth-only would let any host on the LAN feed messages into the bus.

**Drive the outbound dial through a separate Zenoh session with different config.** Rejected. Multiple sessions would multiply both the resource cost and the number of places that need to know which key file to use. The single-session, single-identity invariant is intentional.

**Make Zenoh default to the listener cert as a client cert when no explicit `connect_certificate` is set.** Rejected — not in our control, and even if upstream accepted such a change it would be a behavior break for users who today rely on the missing-client-cert path being explicit.

## Consequences

**Positive**
* Two-machine LAN testing now passes end-to-end: discovery → connect → handshake → ACL admit → agent traffic. The bug class "everything in the GUI looks fine but no messages cross the network" disappears.
* One-line config-builder change. No new files, no new dependencies, no new cleanup obligations.
* Same identity in both directions matches operator intuition: there is one user per workstation and one CN per user.

**Negative**
* The fix is invisible from the GUI — there is no log line that announces "now also presenting client cert on outbound". Diagnosing the original bug required inspecting the Zenoh config dump; the only sign the fix is in place is that messages flow. We rely on integration testing (LAN smoke test) to keep this honest.
* `build_zenoh_config` now writes the cert paths twice. Cosmetic but worth flagging — a future config refactor should probably expose a single `tls_identity` setter that fans out to both pairs, to remove the chance of one half drifting.
