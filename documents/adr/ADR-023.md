# ADR-023: Python + React over Next.js for the Chat Application

**Status:** Accepted
**Project:** DVerse Communication Platform 2.0
**Author:** Denis Lorenzo Neagoe
**Date:** 20-05-2026

---

## Context

The DVerse chat application (`experiments/chat-app`) requires a backend API and a frontend UI. The team evaluated two approaches: a unified Next.js full-stack deployment versus a separated Python (FastAPI) backend with a React (Vite) frontend.

The backend must integrate with Zenoh, SQLite, OpenTelemetry, and a bot presence/bridging layer. These integrations have mature Python libraries (`zenoh-python`, `sqlite3`, `opentelemetry-sdk`, `fastapi`). The platform also already runs Python-based bot agents (`bot_agent.py`, `bot_framework/`), so a Python backend shares the same runtime and dependency surface as the bots.

The frontend serves as a chat UI consumed by the Tauri desktop client. It does not require server-side rendering, static generation, or file-system routing — all of which are Next.js's primary value propositions. The UI state is driven by WebSocket/REST calls to the FastAPI backend rather than server-rendered pages.

## Decision

Use FastAPI (Python) for the backend and React with Vite for the frontend.

The backend runs at `http://localhost:8000` and exposes REST endpoints under `/auth`, `/servers`, `/rooms`, and `/bots`, plus WebSocket message streaming. The frontend runs at `http://localhost:5173` during development and is bundled as static assets for Tauri production builds.

## Alternative Decisions

**Next.js full-stack (API routes + React).** Rejected. Next.js API routes run in a Node.js runtime, which has no first-class Zenoh SDK. Bridging Python-side Zenoh and bot logic into a Node.js layer would require either an additional IPC boundary or rewriting the bot framework in TypeScript — both increase complexity without benefit. Next.js also bundles server-side rendering features that the Tauri-hosted frontend has no use for.

**FastAPI + Next.js frontend (without SSR).** Rejected. Running Next.js purely as a client-side SPA drops SSR but keeps the Next.js build pipeline, which adds complexity (file-system routing conventions, `next/image` optimisation, ISR config stubs) without corresponding benefit when the app is a single-page chat client.

**Django or Flask instead of FastAPI.** Considered. FastAPI was selected over Django because Django's ORM and admin surface are heavyweight for a local experiment. FastAPI was selected over Flask because it provides async support natively, which is required for the Zenoh bridge's `asyncio`-based event loop integration.

## Consequences

### Positive

- Python backend shares the Zenoh SDK and bot runtime with the rest of the platform.
- FastAPI's async model integrates cleanly with the `ZenohBridge` thread/event-loop handoff pattern.
- Vite+React frontend starts and hot-reloads faster than a Next.js dev server for a pure SPA.
- No SSR plumbing that would need to be stripped or disabled for the Tauri build.

### Negative

- Two separate processes (`uvicorn` + `vite`) must be running during development.
- CORS configuration is required for the dev split (handled via `CORSMiddleware` in `main.py`).
- Tauri build must bundle frontend static output and proxy API calls to the Python backend.
