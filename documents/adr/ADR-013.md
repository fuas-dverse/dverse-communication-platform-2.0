# ADR-013: Pydantic Logfire for Structured Logging and Validation Observability

**Status:** Accepted  
**Project:** DVerse Communication Platform 2.0  
**Author:** Abel-Raul Mazilu  
**Date:** 27-05-2026

---

## Context

The ChatApp backend previously had no structured logging. Debug information was emitted via `print()` statements scattered across route handlers, and there was no visibility into Pydantic model validation failures at runtime. Diagnosing data issues in production required log-diving through unstructured text output.

The project already stores sensitive data (password hashes, JWT tokens, bot tokens) in Pydantic models. Any logging solution must ensure these fields are never serialised into log records.

ADR-004 already identified Pydantic Logfire as the structured logging target for chat-mediated agent interactions. This ADR records the concrete implementation decision.

## Decision

Integrate **Pydantic Logfire** (`logfire>=3.0.0`) as the structured logging and tracing layer for the ChatApp backend.

The integration is implemented as follows:

- `backend/observability.py` — single entry point for all Logfire configuration, called once at startup before any FastAPI or route code is loaded.
- `logfire.configure()` — initialises the SDK, reads `LOGFIRE_TOKEN` from the environment. When the token is absent, the SDK emits structured JSON to the console and does not attempt a network connection, so local development works without a cloud account.
- `logfire.ScrubbingOptions(extra_patterns=[...])` — augments Logfire's built-in scrubbing (which already redacts `password`, `token`, `secret`, `api_key`) with `password_hash` and `access_token` to cover the specific field names used in this codebase.
- `logfire.instrument_pydantic(record=...)` — automatically emits a span for every Pydantic model validation. The `record` mode defaults to `'all'` and is overridable via `LOGFIRE_PYDANTIC_RECORD`.
- `logfire.instrument_fastapi(app)` — wraps all FastAPI routes with OpenTelemetry spans for request/response tracing.
- `logfire.instrument_httpx()` — traces all outbound HTTP calls made by the local LLM service.
- `logfire.instrument_anthropic()` — traces all Claude API calls.
- `logfire.span(...)` — explicit spans added around bot response generation (`bot.generate_response`) and each LLM call (`llm.call_claude`, `llm.call_local`) to provide business-level trace context.
- `print()` debug calls in `routes/messages.py` are replaced with `logfire.debug(...)` with structured key-value attributes.

## Alternative Decisions

**Python stdlib `logging` module.** Rejected. It provides log levels and handlers but no structured output, no automatic Pydantic instrumentation, and no distributed trace context propagation.

**OpenTelemetry SDK directly.** Rejected. The OTEL SDK requires significant boilerplate (TracerProvider, exporters, propagators, instrumentors) for the same result. Logfire wraps OTEL and is the approach already named in ADR-004.

**Sentry SDK.** Rejected. Sentry focuses on error capture and is not a general structured logging solution. It would complement Logfire but not replace it.

**Logfire cloud only (require LOGFIRE_TOKEN).** Rejected. Requiring a cloud token would break local development and CI environments with no network access. `send_to_logfire='if-token-present'` keeps the door open for cloud export while keeping console-only output the zero-config default.

## Consequences

### Positive

- Pydantic validation failures now emit structured spans containing the field name, error type, and (scrubbed) input value, making data bugs diagnosable without reproducing them locally.
- Every FastAPI request produces a trace span with method, path, status code, and duration.
- LLM calls (Claude and local Ollama) are traced with bot name, model, and history length, enabling latency analysis per provider and personality.
- Sensitive fields (`password`, `password_hash`, `token`, `access_token`, `secret`, `api_key`) are scrubbed by the SDK before any data leaves the process.
- Local development works without a Logfire account; structured console output replaces unstructured `print()` noise.

### Negative

- `logfire.instrument_pydantic(record='all')` adds a small span per model validation. On high-throughput paths (bulk message imports, SSE stream heartbeats) this adds minor overhead. The `LOGFIRE_PYDANTIC_RECORD=failure` option should be set in production if this becomes measurable.
- The integration depends on Logfire SDK stability. Breaking changes to `logfire.configure` or `instrument_pydantic` would require updates to `observability.py`.

## Scope

| Deliverable | Description |
|---|---|
| `backend/observability.py` | Centralised Logfire setup: configure, instrument Pydantic, httpx, anthropic. |
| `backend/main.py` | Call `setup_logfire()` at startup; add `logfire.instrument_fastapi(app)`. |
| `backend/services/llm.py` | Logfire spans around `call_claude` and `call_local`. |
| `backend/routes/messages.py` | Replace `print()` debug calls with `logfire.debug()`; span around bot response generation. |
| `requirements.txt` | Add `logfire[fastapi,httpx]>=3.0.0`. |
| `.env.example` / `.env` | Document `LOGFIRE_TOKEN`, `LOGFIRE_SERVICE_NAME`, `LOGFIRE_ENVIRONMENT`, `LOGFIRE_PYDANTIC_RECORD`. |
