# ADR-022: Consolidate the router's mTLS identity into a single `tls_identity` helper

**Status:** Accepted
**Date:** 01-06-2026
**Author:** Yordan Mitev

## Context

ADR-017 fixed the silent inter-router handshake stall by setting both halves of Zenoh's TLS config (`listen_*` and `connect_*` certificate / private-key keys) to the same files. The fix was a one-liner pair added next to the existing listener-side pair in `build_zenoh_config`:

```rust
zinsert(&mut cfg, "transport/link/tls/listen_certificate",  ...)?;
zinsert(&mut cfg, "transport/link/tls/listen_private_key",  ...)?;
zinsert(&mut cfg, "transport/link/tls/connect_certificate", ...)?;
zinsert(&mut cfg, "transport/link/tls/connect_private_key", ...)?;
```

ADR-017's own Negative section flagged the structural smell: a router has exactly one identity, but the config surface exposes it as two pairs that have to stay in sync by convention. The four-`zinsert` shape is easy to read but it is also easy to extend incorrectly — anyone adding a new TLS identity key in the future (e.g. switching to per-direction credentials, or replacing rustls with a vendor library that exposes a different key layout) would touch four lines and might forget one. The original ADR-017 bug — "we have a listener cert but no connect cert" — is a present-tense example of exactly that failure mode.

Issue #101 (opened during review of PR #100) tracks the follow-up.

## Decision

Add a `tls_identity` helper next to `zinsert` in `src/zenoh_router/src/router.rs` and replace the four `zinsert` calls with one helper call:

```rust
fn tls_identity(
    cfg: &mut zenoh::Config,
    cert_path: &std::path::Path,
    key_path: &std::path::Path,
) -> Result<()> {
    let cert = json_str(&cert_path.to_string_lossy());
    let key = json_str(&key_path.to_string_lossy());
    zinsert(cfg, "transport/link/tls/listen_certificate",  &cert)?;
    zinsert(cfg, "transport/link/tls/listen_private_key",  &key)?;
    zinsert(cfg, "transport/link/tls/connect_certificate", &cert)?;
    zinsert(cfg, "transport/link/tls/connect_private_key", &key)?;
    Ok(())
}
```

`build_zenoh_config` calls it once:

```rust
tls_identity(&mut cfg, cert_path, key_path)?;
```

No behavior change — the exact same four config keys are still set with the exact same values. The PEM-encoding details (`json_str` quoting) are unchanged. The change is structural: it is no longer syntactically possible to update one of the four without updating all four.

The root CA cert (`root_ca_certificate`) and the `enable_mtls` flag stay as their own `zinsert` calls because they belong to a different identity (the CA, not the router) and to a different concern (transport policy, not credentials) respectively. Bundling them into `tls_identity` would re-introduce the drift risk in a different shape.

## Alternatives

**Leave ADR-017's fix as-is.** Rejected. The four `zinsert` calls work but they encode the listener-vs-connect symmetry as a convention readers have to spot. ADR-017's own Negative section called this out as a follow-up.

**Take the cert / key paths in via a struct parameter on `build_zenoh_config`.** Rejected for this iteration. Bigger refactor, touches every caller of `build_zenoh_config`, and the only field that would benefit from grouping is the cert+key pair — the rest of the parameters (listen address, CA path, admitted list, peers) are independent concerns. If `build_zenoh_config` ever grows past ~10 parameters, revisit.

**Expose the helper as `pub(crate)` so the agent crates (`ping`, `pong`, `bot_framework::node`) can share it.** Rejected. The agent crates only ever act as TLS clients — they need just the connect-side pair, not both. Their config path (`NodeConfig::mtls`) doesn't currently suffer the listener / connect-half drift problem because there is no listener half to forget.

**Use a builder pattern (`TlsIdentity::new(cert, key).apply(&mut cfg)?`).** Rejected. One-shot helper, no configurability — the construction step would add zero information and one allocation.

## Consequences

**Positive**
* The router's mTLS identity is set in one place. Adding a new TLS-identity key in the future (rotation timestamp, OCSP staple, etc.) means editing one function, not finding all the call sites.
* `build_zenoh_config` is shorter (4 lines → 1) and reads at the same level of abstraction throughout — every line is "one config concern", not "one config key".
* The accompanying comment block from ADR-017's fix moves into the helper, where it is closer to the code it describes and can't drift to a different position than the lines it explains.
* Resolves the open follow-up that was tracked in issue #101 and flagged in ADR-017's Negative section.

**Negative**
* One extra layer of indirection when reading `build_zenoh_config` top-to-bottom: the reader has to jump to `tls_identity` to see which four keys are being written. Mitigated by the helper's doc comment which lists them.
* If the cert and key ever do need to differ between listener and connect direction (a use case we have no current plans for), the helper's signature has to change. Acceptable — that change would be a deliberate decision, not an accidental drift.
